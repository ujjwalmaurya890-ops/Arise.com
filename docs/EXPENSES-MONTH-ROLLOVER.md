# Expenses widget — calendar-month rollover

Status: implemented and verified in this repository. Last verified: 2026-10-27.

## 1. Where the behaviour lives

The Expenses widget is one source file, `src/expenses.js` (minified, single IIFE,
mounted through `window.__mountExpenses(host)` / `window.__unmountExpenses(host)`).
It is shipped through the generated chunk listed in `index.html` (`w11.*.js`,
built by `scripts/tools/build-widget-chunks.cjs`).

Month handling is a single, shared set of helpers at the top of the file:

| Purpose | Function | Line (src/expenses.js) |
| --- | --- | --- |
| Local calendar month id (`YYYY-MM`) | `exwCurrentMonth()` (via `Q(y, m0)`) | 4 |
| Month id from a transaction date | `le(date)` → `date.slice(0, 7)` | 1 (helpers block) |
| Selected month (falls back to current) | `exwViewMonth()` | 5 |
| Month arithmetic, incl. year boundary | `exwMonthShift(id, ±n)` | 7 |
| Month-scoped rows | `exwInMonth(list)` | 8 |
| Selected-month income/expense/net | `exwMonthTotals(list)` → `ee(list, month)` | 9 |
| Month picker + prev/next/"This month" | `exwMonthBar()` | 15 |
| Available months (history + current) | `exwMonthOptions()` | 10 |
| Rollover on init/focus/pageshow/visibility | `exwCheckMonthRollover()` | 14 |
| Rollover on every render | `exwMonthChangeGuard()` | 13 |

There is **no monthly reset job and no deletion**. A new month is empty because no
stored transaction has a date in that month; the same transaction array is filtered
by `le(t.date) === exwViewMonth()` everywhere a monthly figure is produced:

* Overview summary — `exwMonthTotals()` → `oo()` (both inside the minified block on line 17).
* Category / payment-method / income-source donuts — `Do()`, `io()`, `so()` are
  called with `exwInMonth(all)`, so each chart only sees the selected month.
* Overall monthly budget card — `lo()` uses `ee(all, exwViewMonth()).expense`.
* Per-category monthly budgets — `pl()` uses `Ie(all, exwViewMonth())`.
* Budget history (last 6 months) — `xl()` uses `Ie(all, month)` per month.
* Income-vs-Expense monthly budget strip — `qo()` uses `ee(all, exwViewMonth())`
  (changed in this work; it previously hard-coded the real current month).
* Transactions list, search, sort and filters — `ts()` filters through `Mt()`
  (`le(t.date) === exwViewMonth()`).

Recurring transactions are generated by `kn()` (line 17, offset ~25740) on every
widget mount. Each template stores `lastGeneratedPeriod`, generation starts at the
month **after** that watermark and stops at "today", so mounts and rollovers are
idempotent.

## 2. What was already present vs. what changed

Already present at commit `d152930` and left intact:

* Calendar-month filtering and `YYYY-MM` ids, history preserved, no destructive reset.
* Month selector (previous / next / picker / "This month"), labelled "Current month"
  vs "Viewing history", plus per-month empty state in the transaction list.
* Rollover detection on mount, `focus`, `pageshow`, `visibilitychange` and a 60 s
  interval for a tab left open across midnight.
* Month-scoped budgets (global configuration, per-month usage), recurring-template
  idempotency, CSV/JSON export, CSV import with id de-duplication, cloud backup
  allow-list (`src/cloud/storage-schema.js` already lists every expense key,
  including `arise-expenses-v1` and `arise-expenses-month-seen-v1`).

Changed in this work (smallest safe edits):

1. **`src/expenses.js` — month re-check on every render.**
   `b()` now starts with `exwMonthChangeGuard()`. Previously a render triggered by
   changed data (storage-watch bus) in a month that changed while the tab stayed open
   could keep showing the old month until a focus/visibility event. The guard is
   side-effect free when the calendar month has not changed.
2. **`src/expenses.js` — safe split of the rollover check.**
   `exwMonthChangeGuard()` is the render-safe part (drop a stale selected month when
   the calendar month changed). `exwCheckMonthRollover()` keeps the init-time cleanup
   of an impossible future `exw-month-filter` and then delegates to the guard. This
   keeps the existing "a future-dated month can still be viewed" behaviour that the
   date-boundary tests rely on.
3. **`src/expenses.js` — Income-vs-Expense budget strip follows the selected month.**
   `ee(e, re())` → `ee(e, Ki())`, and the label now names the month
   (`October 2026 Budget`) instead of the ambiguous "This Month's Budget". For the
   current month the numbers are identical to before.
4. **Generated artifacts regenerated** (`assets/chunks/w11.*.js`, `index.html`
   chunk list/map, `service-worker.js` shell list) via `npm run build:chunks`.
5. **`tests/test-expenses-monthly-reset.js`** extended from 12 to 18 suites.

## 3. Storage contract (unchanged)

* `arise-expenses-v1` — transaction array. `{ id, title, amount, type: "expense"|"income",
  category, incomeSource?, date: "YYYY-MM-DD", paymentMethod, tags?, note?,
  createdAt?, recurringId?, splitGroup?, splitFromTitle? }`. Recurring templates live in
  `arise-expenses-recurring-v1` and carry `dayOfMonth`, `active`, `lastGeneratedPeriod`. `splitGroup` / `splitFromTitle`
  are added by the split action (the original row is replaced, so totals never
  double-count).
* Month-related UI state only: `exw-month-filter` (selected month; removed for the
  current month) and `arise-expenses-month-seen-v1` (last calendar month the widget
  observed). Rollover writes/removes only these two keys.
* Budgets are global settings (`arise-expenses-monthly-budget-v1`,
  `arise-expenses-budgets-v1`, `arise-expenses-weekly-budget-v1`) — usage is
  per-month, the configuration is never rewritten by month navigation.

## 5. Known limitations

* **Forecast** (`So()`) and **Runway** (`mo()`) on the Overview tab are current-state
  metrics: Forecast projects the real current month's burn rate, Runway uses the
  lifetime balance. They are explicitly worded that way in the UI (the forecast note
  names the month it projects) and are intentionally not re-scoped to a browsed
  historical month.
* **Weekly** budget/income-vs-expense views are week-based by design; only the
  monthly strip follows the selected month.
* Recurring occurrences are generated on widget mount (existing design). A tab left
  open across midnight picks up the new month immediately, and the recurring entry
  for the new month is created on the next mount/refresh — never twice.
* The month picker lists months that contain transactions, so a transaction dated in
  a future month is viewable; the "next" arrow still stops at the current month.
