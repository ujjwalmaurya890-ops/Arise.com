# Arise.com — performance overhaul (Phase 25 report)

Date: 2026-11-22
Branch: `arena/15174d19-arise-com` (from `c4f02d1` on `main`)
Author: engineering pass requested by the project owner

This is the closing report of a 25-phase performance programme: audit, measurement,
prioritised fixes, implementation, verification. Every number below was produced by a
script that is checked into this repository (or by the probes listed at the end) and can
be reproduced. Where a metric could not be measured honestly, it is marked
**Not measured** instead of being estimated.

---

## 1. Executive summary

The application shipped ~126 widget/source files and executed them all during boot. The
single largest problem was therefore **startup work**, not bytes: the dashboard was
visually complete in a few hundred milliseconds but only became *interactive* (widgets
mounted, lazy routes resolvable) seconds later — 2.6–4.5 s on an idle desktop and never
inside a 6 s window on a 4×-throttled phone.

What changed:

1. **A route-scoped chunk scheduler** replaced the "load every widget script in order"
   loader. Boot now touches **3 of 12 chunks** (671 KB raw / 194 KB gzip of a
   2.8 MB / 749 KB payload); the rest stream in afterwards, one chunk at a time, and any
   route the user actually opens pre-empts the background queue and loads only the chunk
   that owns that route's widgets.
2. **Readiness semantics were fixed**: `__ariseWidgetsReady` now fires when the widgets of
   the *current screen* are mounted (previously only after the hundredth unrelated widget
   script had executed), with `__ariseWidgetsSettled` / `__ariseAllWidgetsSettledAt` kept
   for "everything attempted".
3. **Execution pacing** was rebuilt around `setTimeout` with explicit gaps (rAF and
   `requestIdleCallback` were measured to stall for seconds during React commits), startup
   chunks run back to back, background chunks are paced and back off after real input.
4. **Mount stubs became chunk-aware**, so a demand-loaded route either loads its chunk, or
   shows a reserved skeleton, or reports a real failure — never a permanently dead panel.
5. **Chunk failures recover on reconnect** instead of leaving routes un-mountable until a
   manual reload.
6. **A layout-shift regression found by the project's own browser gate was fixed** at the
   source: the page quick-jump/filter bar is now created (hidden) before the route body
   lays out, so inserting it no longer moves the dashboard. Boot CLS in
   `scripts/verify-loading-browser-e2e.cjs`: 0.1461 (failing) → **0.0025–0.0030 (passing)**.

Measured result (medians of 3 runs, see §6 for the full tables):

## 2. Constraints honoured

* No redesign, no new visual identity, no UI rework. The only DOM the work adds is a
  *hidden* copy of an element that already existed (the page widget bar), which is then
  populated exactly as before.
* No functionality removed; all 20 navigation destinations were re-checked (§8), the
  `?chunks=0` / `arise-chunks=off` legacy path still loads individual source files.
* No new runtime dependencies (the chunk manifest is generated by an existing build step;
  probes use the already-installed `playwright-core` + `@sparticuz/chromium`).
* No duplicate implementation: the loader keeps its manifest, ordered-execution
  guarantee, ordered source-file fallback, failure reporting and retry hooks.
* No unverified claims: every figure below has a reproducing command.
* Business logic untouched: storage keys, sync, backup, exam/placement calculations were
  not modified.

## 4. Prioritised findings that drove the work

**P0 — boot executed the entire widget payload.** 126 source files, 2.8 MB raw, were
injected as `<script async=false>` in batches with 100–260 ms gaps between them; anything
that needed a widget (toolbar, shortcuts, theme controls) waited for the whole list.
Measured: dashboard ready 2623–4467 ms desktop, never inside 6 s at 4×/Slow-3G.

**P0 — the same work blocked input.** Executing every chunk back-to-back (the naive fix)
pushed interaction latency past 500 ms on throttled devices; the loader's own comment
records ~2.5 MB compiled and executed in one burst.

**P1 — readiness was defined as "everything loaded".** `__ariseWidgetsReady` fired only at
the end of the list, so every consumer (enhancer, a11y patches, skeleton replacement,
theme controls) inherited the full payload latency — and mount stubs could not tell the
difference between "not loaded yet" and "will never load".

**P1 — chunks could not be loaded individually.** The generated chunk manifest had no way
to map a `__mountX` hook to the chunk that provides it, so on-demand loading was
impossible without executing the whole list. A static dependency scan was tried first and
**rejected** (§7) because widget files capture globals through local aliases of `window`.

**P2 — a failed chunk was terminal.** A dropped connection left the affected routes with
mount errors for the rest of the session; the only recovery was a full reload.

**P2 — the enhancer re-ran full widget discovery on every mutation burst.** On a
4×-throttled phone this was ~174 ms (9.3 %) of main-thread time during boot.

**P3 — layout stability of the injected toolbar.** Inserting the page quick-jump bar after
the route body had painted moved the whole content column (~42 px desktop / ~75 px at
390 px). This was latent in the original code and only became visible once the dashboard
painted earlier.

## 5. What was implemented

### 5.1 Route-scoped chunk scheduler — `src/boot/widget-loader.js` (rewritten)

* `chunkState` / `pendingChunks` / `inFlight` queue; chunks execute **in manifest order**
  (preserving the ordered-execution contract the old loader guaranteed), one at a time.
* `enqueueThrough(url, urgent)` — demand loads keep manifest order while pre-empting the
  background queue; `expediteAll()` for capture scripts and verification.
* Startup set = manifest `core` (w01–w03, 671 KB raw / 194 KB gzip). Startup chunks run
  **back to back** (`gap = 0` while `urgent || !coreDone`); this alone took desktop
  core-ready from 4.6 s to ~0.9 s in the A/B probe.
* Background chunks: fetch starts early (native `preload`, low priority) so a route the
  user opens finds its bytes in the HTTP cache, but **execution** is paced
  (`BACKGROUND_GAP` 400 ms, 1500 ms on low-power devices, 2500 ms right after real input),
  via `setTimeout` — rAF and `requestIdleCallback` were measured to stall for seconds
  while React commits and were rejected.
* Data-saver / 2G connections skip the speculative background fetch entirely.
* `notifyCoreReady()` — `__ariseWidgetsReady` / `arise:widgets-ready` fire when the current
  screen's chunks are done, `__ariseWidgetsSettled` / `arise:widgets-settled` when every
  chunk has been attempted. `__ariseCoreWidgetsReady(At)` added for instrumentation.
* `window.__ariseLoadForMount(name)` / `__ariseMountChunk` / `__ariseMountChunkFailed` for
  the mount stubs; `window.__ariseExpedite()` for capture/verification; legacy
  `?chunks=0` / `arise-chunks=off` path preserved.
* `bindOnlineRetry()` — a chunk that failed because the network dropped is cleared and
  re-queued in manifest order on the `online` event instead of waiting for a reload.

### 5.2 Chunk-aware mount stubs — `src/boot/mount-stubs.js`

A stub now distinguishes *pending* (chunk still streaming → keep the reserved skeleton),
*loading* (chunk being executed → skeleton) and *failed* (`chunkState === "failed"` →
report, then render the error state), and calls `__ariseLoadForMount` to pull the exact
chunk that owns the widget. The unmapped-panel fallback is keyed to `__ariseWidgetsReady`
(not Settled) so data-saver connections stop showing skeletons for panels that will never
load.

### 5.3 Enhancer scan coalescing + bar reservation — `src/saas-widget-enhancer.js`

* Repeated "the toolbar is still missing" rescans are coalesced (trailing 140 ms debounce,
  one immediate scan per 250 ms while the bar does not exist). Saves ~174 ms of
  main-thread time on a 4×-throttled phone during boot while still letting the bar be
  created on the first structural mutation.
* **Bar slot reservation** (CLS fix): the bar element is created hidden — with placeholder
  chips so its height matches the populated bar at every breakpoint (44 px single row,
  ~116 px two rows below 600 px) — as soon as the route header exists, and is merely
  un-hidden when the real chips are available. It is *not* dropped while the widget
  payload is still streaming, and it is removed (as before) on routes that genuinely have
  fewer than three widgets once the payload has settled. `ensureBar()` was extracted so
  the markup and handlers exist once.

### 5.4 Chunk manifest — `scripts/tools/build-widget-chunks.cjs`

Emits `scripts, chunks, chunkFiles, core, mountChunks` (29 mount hooks → owning chunk).
`core` is the startup set; `mountChunks` is what makes on-demand loading possible. The
static `chunkRequires` inference was removed (rejected, §7).

### 5.5 Browser gate — `scripts/verify-loading-browser-e2e.cjs`

The connectivity check now waits for `__ariseWidgetsSettled` (bounded) before it pulls the
network, and same-origin failures/console errors caused by that deliberate outage are
ignored while it is offline. Rationale: `__ariseWidgetsReady` legitimately fires before the
background chunks finish; the check is about the offline banner, not about racing the tail
of the payload. Everything else in the gate is untouched and still fails on any real
same-origin failure.

### 5.6 Test update — `tests/test-saas-upgrade.cjs`

The toolbar assertion now waits for the *populated* bar (≥3 chips) instead of the bare
element, because the element legitimately exists earlier as a hidden placeholder. The
assertion itself is unchanged.

## 7. Experiments that were measured and rejected

1. **Deferring six non-critical stylesheets** (`media="print"` + `<noscript>` fallback for
   day-plan, focus-session-audit, study-horizon, progress-overview, notification-center,
   dashboard-personalization). LCP gain at 4×/Slow-3G: 1952 → 1920 ms (~30 ms), but the
   promoted sheets re-laid-out the already-painted dashboard: CLS 0.0227 extra at 1440 px
   and 0.1459 at 390 px in a single run. Re-measured with the sheets blocking again: FCP
   1492–1644 ms, LCP 1724–1868 ms — i.e. *better* than with the deferral on this machine.
   **Reverted**; `index.html` keeps its original stylesheet list.
2. **Static dependency inference between chunks** (`chunkRequires`): widget files capture
   globals through local aliases of `window`, so any static scan produced false negatives
   that broke initialisation order. Replaced by the runtime `mountChunks` map plus
   "demand loads keep manifest order".
3. **`requestAnimationFrame` / `requestIdleCallback` pacing**: both stall for seconds when
   the page is not compositing (background tab, long React commit); the ordered queue
   stopped dead. Replaced by `setTimeout` with explicit gaps.
4. **`fetch().arrayBuffer()` prewarming**: allocated unused copies and could download a
   chunk twice; replaced by native `<link rel=preload as=script>`.
5. **Loading every chunk immediately (expedite everywhere)**: TBT regressed badly on
   throttled devices; kept as an opt-in (`__ariseExpedite`) for capture/verification.

## 9. Remaining bottlenecks / known issues

1. **Mobile TBT is still high** (1.1–1.7 s at 4× CPU). The chunk scheduler stops *executing*
   unused routes during the first seconds, but the React shell, the enhancer, the theme
   system and the first-wave widgets are still a lot of work for a slow core. ~735 ms of
   the profile remains in `(program)` and could not be attributed; without that
   attribution any optimisation would be guesswork.
2. **Mobile "settle" often is not reached inside 6 s** on the emulated slow connection
   (background chunks keep arriving). That is by design, but it means an on-demand route
   opened in that window may still load one chunk before its widgets appear.
3. **CSE Syllabus shows two "Panel unavailable" slots** — pre-existing on `c4f02d1`, not
   caused by this work, not fixed here (needs a product decision about the two configs).
4. **Per-route CSS is still a single 82 KB bundle** (13 KB gzip). Splitting it by route was
   measured in experiment 1 and rejected because of the layout shift; a proper split needs
   route-aware critical CSS, which is a larger change.
5. **`__ariseWidgetsReady` semantics changed.** Consumers that assumed "everything is
   loaded" must use `__ariseWidgetsSettled` / `arise:widgets-settled`. All in-repo
   consumers were updated (enhancer, a11y patches, skeleton fallbacks, gate); third-party
   scripts are not a concern here but the change is documented in the loader.
6. **The bar reservation is a mitigation.** The page quick-jump bar is still created by
   JavaScript after the route exists. Reserving its strip keeps CLS at parity, but the
   cleaner long-term fix is to render the strip in the route shell so no reservation is
   needed.

## 10. Next steps (in priority order)

1. Attribute the remaining `(program)` time in the mobile profile (self-time edges with
   `--no-source-map` builds and a longer capture) and only then optimise it.
2. Move the page quick-jump bar into the route shell (React) and drop the reservation.
3. Route-split the styles bundle *after* adding route-aware critical CSS, verifying CLS at
   390 px and 1440 px.
4. Add a real-user (RUM) INP/LCP beacon so field numbers replace lab maxima.
5. Re-run this pass's probes on a physical mid-range Android before any further mobile
   claims.
